## Matrix Naming Conventions

| Symbol | Definition |
| :--- | :--- |
| **$A$** | **Evaluated Dataset:** The complete matrix of features (e.g., $\nabla^2\phi$) calculated by the neural network across all physical coordinates.|
| **$A_{r}$** | **Regularization Block:** The static identity matrix ($\sqrt{\lambda}I$) .
| **$A_{aug}$** | **Augmented Matrix:** Matrix stacking $A$ and $A_r$ vertically. 
| **$A_B$** | **Mini-Batch Submatrix:** Matrix sampled from $A_{aug}$ (e.g., 500 rows). |
| **$A_{raw}$** | **Raw Coordinates:** The physical grid points $(x,y)$ and boundary locations.|

## Background
Previously, we evaluated the entire dataset and created a massive master matrix $A_{aug}$. We then implemented sketch-and-project algorithms (Block Kaczmarz) to solve it without needing to compute an even larger $A^TA$ matrix. While this sped up the math, it did not solve the root problem: building the underlying $A_{aug}$ matrix in the first place causes Out-Of-Memory (OOM) crashes as the grid density scales. 

We show 3 approaches here to tackle this.

### 1. Sample Features on CPU
**Strategy:** Compute on GPU, Store on CPU.
We load $A_{raw}$ (coordinates) onto the CPU and send them to the GPU in chunks to compute the features (`f_xx` and `f_yy`). Because the GPU VRAM is small, we immediately transfer the calculated chunks back to the CPU. However, we do not assemble $A_{aug}$, but we use stratified sampling on `pde, fy_bc, f_bc, lambda_I` and send the sampled $A_B$ to the GPU for sketch-and-project.
* **Pros:** We evaluate the network and calculate the PDE derivatives exactly once. 
* **Cons:** Every iteration, data is moving from CPU and GPU, creating a lot of latency. Also, we need .block_until_ready() because python for loop will send too much data to JAX and cause VRAM fragmentation. Another problem is that, while this method saves GPU VRAM, it will cause a CPU OOM if the dataset ($A_{raw}$) scales too big.

### 2. Store and Sample Raw Coordinates $A_{raw}$ on GPU
**Strategy:** Store $A_{raw}$ on GPU, evaluate $A_B$ on the fly.
We push the entirety of $A_{raw}$ into the GPU VRAM (if it is able to fit) and keep it there. The GPU generates its own random PRNG keys, samples the indices, slices the coordinates, and evaluates the forward pass to generate $A_B$ on the fly, does sketch-and-project, and immediately deletes $A_B$.
* **Pros:** Lower PCIe transfer overhead. $A_{aug}$ never exists, completely solving the VRAM crash.
* **Cons:** The GPU must recalculate the exact same PDE derivatives for the same coordinates over and over again across epochs, making training longer. 

### 3. Store and Sample Raw Coordinates $A_{raw}$ on CPU
**Strategy:** Load and sample on CPU (or with dataloaders), calculate mini-batches on GPU.
For very big datasets (e.g., 100GB) where $A_{raw}$ cannot fit in memory, the data is kept sharded. The CPU fetches shards into System RAM, samples a shard to extract a batch of raw coordinates, and transfers that small block of $A_{raw}$ to the GPU. The GPU evaluates $A_B$ on the fly, solves, and deletes it. 
* **Pros:** Can theoretically train on infinitely large datasets. Maximum memory efficiency. 
* **Cons:** Re-calculates PDE derivatives every epoch. Requires optimized data-loaders (eg. from PyTorch or Tensorflow) to prevent the GPU from sitting idle while the CPU reads from the SSD.

### 4. Approximate DPP Sampling (Store $A_{raw}$ on CPU)

### 5. Streaming Gram Assembly
**Strategy:** Calculate features on the fly, accumulate into a small Gram matrix, sum gram matrices and solve directly.

In a Physics-Informed Random Feature Model (FrPINN), the hidden weights are frozen. Iterative sketch-and-project methods like Block Kaczmarz were originally implemented to avoid calculating the big Gram matrix $A^TA$. However, the reason $A^TA$ causes OOM is because the construction and holding of $A$ matrix in memory. This method, makes it so that we do not calculate the $A$ at all. We solve the Tikhonov-regularized Least Squares normal equation directly:
$$w = (A^T A + \lambda I)^{-1} A^T b$$

Instead of building the $N \times m$ global matrix $A$, we stream the raw dataset ($A_{raw}$) in mini-batches. For each batch, we evaluate the network to get a tiny feature matrix $A_k$, compute its inner product $A_k^T A_k$, and add it to a running total in VRAM. We immediately delete $A_k$. By the end of the dataset, we constructed the $m \times m$ Gram matrix without $A$ ever existing in memory.

**Implementation Details:**
1. Initialize an $m \times m$ matrix $H$ (Hessian/Gram) and an $m \times 1$ vector $g$ (gradient) with zeros in VRAM. These must be initialized in `float64` to prevent floating point cancellation when summing millions of values.
2. Stream raw coordinates ($A_{raw}$) to the GPU in batches.
3. Evaluate the PDE/BC features to get $A_k$.
4. Compute $A_k^T A_k$ and add to $H$. Compute $A_k^T b_k$ and add to $g$.
5. Garbage collect $A_k$.
6. Once the dataset is complete, simulate $A_r$ by adding $\lambda I$ to $H$. 
7. Solve $Hw = g$ using `jnp.linalg.solve`.

* **Pros:** Features are evaluated exactly once. Flat memory footprint restricted strictly to $O(m^2)$, entirely eliminating OOM crashes regardless of dataset size ($N$). Solves instantly without requiring epochs or a learning rate ($\alpha$).
* **Cons:** If m is very large, this will cause still cause OOM problems. There will be floating point problems as condition number is squared: $\kappa(A^T A) = \kappa(A)^2$

## Tackling a larger $A$ matrix
### Sampling
When the $A_{aug}$ matrix becomes large, the number of internal PDE points can vastly outnumber the boundary conditions as grid density increases. Purely uniform random sampling may therefore cause the solver to statistically under-represent the boundary constraints.

To address this, we try 2 methods.
1. Uniform Random Sampling with replacement
2. Stratified Sampling with replacement
    Boundary conditions can be sampled with higher weighting.

    *Example Batch Composition*

    | Component                    | Batch Size | Sampling Mechanic |
    |------------------------------|------------|-------------------|
    | PDE Batch                    | 350 rows   | Random with replacement |
    | Neumann BC Batch             | 50 rows    | Random with replacement (Oversampling) |
    | Periodic BC Batch            | 50 rows    | Random with replacement (Oversampling) |
    | $L_2$ Regularization Block   | 50 rows    | Random sample from static identity matrix |
